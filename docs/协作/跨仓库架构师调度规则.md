> 归属：`dongdongxiaozu/fenbushijiaohu` ISSUE #3

## 0. 一句话结论

> 跨仓库调度架构师，**必须携带完整的目标定位（仓库路径 + 角色名）+ 项目上下文（任务书 + 相关文件 + 接力卡）**。只写 `@架构师` 会因定位模糊导致调度失败或串库；写成 `@仓库/架构师(角色名)` 并附上下文，才能精确、稳定地把架构师从它所在的仓库"调度"过来，真正实现跨项目协作。

---

## 1. 为什么"带仓库"比"只带角色"更能跨项目调度

### 1.1 定位精确性（命中唯一）
| 写法 | 能否唯一定位 | 说明 |
|------|------------|------|
| `@架构师` | ❌ 模糊 | 平台上有多个仓库都定义"架构师"角色，仅凭角色名可能串库/误触发 |
| `@dongjiagoushi` | ⚠️ 半明确 | 指向仓库，但缺角色名，可能命中仓库内多个架构角色（总师/经理/评审…） |
| `@dongdongxiaozu/dongjiagoushi(架构·总师)` | ✅ 唯一 | **仓库路径 + 角色名**双定位，精确命中"总师"这个具体角色 |

### 1.2 上下文携带（可调度 + 可接力）
- 只写 `@架构师` 时，架构师**不知道你的项目背景**，需要重新澄清，调度成本高。
- 带仓库 + 附上**任务书 / 相关文件 / 接力卡**，架构师一到即可基于项目上下文续跑，实现真正的"跨项目调度"。

### 1.3 跨仓库协作的本质
> 架构师"长在"它自己的仓库（`dongjiagoushi`），通过 `@仓库路径(角色名)` 从那里被"调度"到你的项目仓库参与协作。**携带仓库路径，就是给调度指路；携带角色名，就是给调度点人；携带上下文，就是让调度落地。**三者缺一不可。

## 2. 标准召唤格式（规范模板）

```
@{仓库组}/{仓库名}({角色名})  <任务书>

**任务书**
- 目标：<要做什么、为什么>
- 边界：<做/不做什么>
- 验收标准：<如何判定完成>

**输入上下文（相关文件）**
- <文件路径或仓库内资源，尽量带具体路径>

**约束条件**
- <技术栈 / 规范 / 安全红线，如"不输出 Token"等>

**期望结果**
- <交付物形式 / 留痕方式>

---
接力卡
任务书:  <一句话任务>
输入上下文: <前置产物/上下文>
当前进度: <已进行到哪一步>
下一步: <接手后做什么>
接手角色: <角色名>
输出契约: <交付物/格式>
---
```

## 3. 三种调度场景速查

### 3.1 同仓库内调度（角色切换）
> 架构师在自己仓库内调度协作角色（PM/DEV/CR/QA）。
```
@CodeBuddy 调用 architect skill，做 <系统/模块> 的架构设计
[触发:架构·开发] 实现 auth 模块，边界=仅后端，验收=单测通过
```

### 3.2 跨仓库调度（把架构师从 dongjiagoushi 调度到本项目）—— 本次重点
> 推荐写法：**仓库路径 + 角色名 + 完整上下文**。
```
@dongdongxiaozu/dongjiagoushi(架构·总师) 请用你的架构八步体系，复查 <本项目> 的 <文档/模块>，形成新框架。
任务书: ... / 输入上下文: ... / 接力卡: ...
```

### 3.3 跨仓库调度的"描述规则"三原则
1. **先指路再点人**：一律写 `@仓库组/仓库名(角色名)`，不省略仓库路径。
2. **带上下文**：至少附任务书 + 相关文件路径；复杂任务补接力卡。
3. **留痕可回溯**：调度产出留痕在本项目 Issue/PR 评论，便于后续接力。

## 4. 常见错误与修正

| ❌ 低效写法 | 问题 | ✅ 推荐写法 |
|------------|------|------------|
| `@架构师 帮我设计` | 定位模糊、无上下文 | `@dongdongxiaozu/dongjiagoushi(架构·总师) 请复查项目 X 的架构，任务书: ...` |
| `@dongjiagoushi` | 仓库内多角色，未点人 | `@dongdongxiaozu/dongjiagoushi(架构·评审) 请评审 ...` |
| `@dongdongxiaozu/dongjiagoushi(架构·总师) 帮我看看` | 有点名但无项目上下文 | 补上 `输入上下文: docs/architecture/*` 与 `接力卡` |
| 只 `@` 不说明要调度谁过来 | 架构师不知为何被点 | 说明"请从 dongjiagoushi 调度架构·总师过来参与 X 项目的复查" |

## 5. 跨仓库协作流程（本次落地的增强线路）

```
项目仓库 A（fenbushijiaohu）
    │ ① 发出调度请求：@dongdongxiaozu/dongjiagoushi(架构·总师) + 任务书 + 相关文件
    ▼
架构师仓库（dongjiagoushi）
    │ ② 架构师被"调度"过来，读取任务书与输入上下文
    │ ③ 用其架构八步/四级粒度方法论产出结论
    ▼
项目仓库 A（fenbushijiaohu）
    │ ④ 架构师结论留痕在本项目 Issue/PR 评论
    │ ⑤ CodeBuddy 协同沉淀为新框架文档（如 12-整体架构分层设计.md）
    ▼
闭环：跨仓库协作完成，产物回到本项目，可继续接力
```

> 这套"调度规则"让架构师**从它所在的仓库稳定地被调度到任意项目**，实现更强的跨仓库协作——这正是比"只带 @架构师"更强的地方。

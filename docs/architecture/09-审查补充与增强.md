## 0. 一句话结论

> 现有六层架构**骨架正确**，但把「节点不稳的容错、P2P 中转加速、数据异地冷备、防刷分的信誉分、社区治理」当成了"边角"，这恰恰是**能否真正规模化/可信赖的关键**。本文针对这 6 项逐一补齐设计，全部以**增量模块**方式挂载到现有分层，不推翻原架构。

## 2. 补强设计 ①：网络稳定性 / 容错冗余（E1）

**核心思想：把"贡献节点"从单点信任升级为"冗余服务簇"，任一节点不稳不丢服务。**

新增模块：`transport/health`（健康检测）+ `transport/failover`（故障切换）+ `redundancy`（冗余度）

### 2.1 节点健康检测（Health Probe）
- 每个节点周期性广播**心跳 + 负载 + 在线时长**（`topic://net/heartbeat`）。
- 收方用「最近 N 次心跳窗口」计算节点可用率 `availability = 成功心跳/应有心跳`。
- 低于阈值（如 <90%）的节点被标记为**不稳节点**，调度器减少其派单权重。

### 2.2 冗余度与副本（Redundancy）
- 重要数据/任务设**副本数 R≥3**，由 `compute` 分配到不同物理节点。
- 任一副本节点失联 → 其余副本**自动接管**，结果取多数一致，服务不中断。

### 2.3 故障切换（Failover）
```
节点 A 失联
  → 健康检测标记 A 不可用
  → A 的任务/会话漂移到备用节点 A'
  → 客户端自动重连 A'（信号层做会话迁移）
  → 全程用户无感，仅提示"已切换到备用节点"
```

### 2.4 稳定节点激励
- 高可用率 + 长在线时长 → 信誉分加成 → 优先承接任务/获得更多带宽配额（形成"越稳越被用"的正循环，见 §6）。

## 3. 补强设计 ②：P2P 中转加速（E2）

**核心思想：把"纯消费者的电脑"和"带宽富余的节点"变成中转/加速中继，复用现有链路做多路径转发，类似 P2P 加速/CDN 去中心化。**

新增模块：`transport/relay-mesh`（中继网格）+ `transport/multipath`（多路径）

### 3.1 中继网格（Relay Mesh）
- 任何节点在**空闲算力/带宽富余**时可声明成为"志愿者中继"（`topic://net/relay/offer`）。
- 中继节点只做**转发不落盘**，收 A 的数据转发给 B，加速弱网/跨区直连。
- 与 TURN 的关系：TURN 是**付费兜底**，志愿者中继是**免费/积分激励**的社区加速，两者并存、按成本优先志愿者中继。

### 3.2 多路径（Multipath）—— 真正的"P2P 加速"
- 同一内容从**多条路径**同时拉取（直连 + 1~2 个志愿者中继），取先到者/合并分片。
- 类似 BT/迅雷多源下载：`content` 分片后，每片可来自不同中继节点。
- 视频播放 = 边下边播 + 多源冗余，弱网也能流畅。

### 3.3 中转激励
- 转发流量计入"贡献量"→ 换算信誉分/带宽配额（需防流量刷量，见 §6.3 双重校验）。

## 4. 补强设计 ③：数据持久化 / 云端 / 115 冷存储备份（E3）

**核心思想：本地优先不排斥"异地冗余"。三明治式存储 = 本地热存 + 云端热存/中存 + 115 冷存归档。**

新增模块：`storage/sync`（云端同步）+ `storage/archive`（冷存归档）

### 4.1 分层存储策略
| 层 | 载体 | 存什么 | 用途 |
|----|------|--------|------|
| **L0 本地热存** | 本地 DB | 高频会话、近期视频分片 | 秒开、离线可用 |
| **L1 云端热存/中存** | 自建云 / 对象存储(S3 兼容) | 评论、视频元数据、签名账本 | 多端同步、容灾 |
| **L2 冷存归档** | **115 网盘（长期冷备份）** | 全量历史评论、视频归档、信誉快照 | 长期备份、防丢失 |

### 4.2 对接 115 冷存储（对接方案）
- 115 开放 API（需用户授权 OAuth，自愿开启）作为**归档后端**。
- 归档策略：
  1. 本地数据**加密后**（用户私钥加密，见 §7 安全）打包成归档块；
  2. 定期（如每 7 天）将增量 `评论 + 视频元数据 + 信誉快照` 上传到 115 指定目录；
  3. 仅存**加密归档**，115 侧无法读取明文（隐私可控）；
  4. 提供"一键恢复"：从 115 拉取归档解包还原到本地/云端。
- **取舍**：115 冷存定位"防丢失"而非"热读"，避免把高延迟冷存当在线存储用。

### 4.3 一致性：云/本/冷三处如何对齐
- 以**签名账本（append-only 日志）**为事实源：本地写 → 追加到账本 → 同步云端 → 定期打包进冷存。
- 任何一端可回放账本重建全量数据（复用 CRDT 收敛）。

## 5. 补强设计 ④：社区治理（E4）

**核心思想：治理不靠单一中心裁判，靠"信号聚合 + 分级处置 + 透明留痕"，核心目标是筛出正常用户、识别恶性个体。**

新增模块：`governance/moderation`（治理）+ `content/report`（举报）+ `governance/verdict`（裁决）

### 5.1 恶意信号采集（多信号，不只靠举报）
- **内容侧**：文本/图像分类（敏感、辱骂、广告、诈骗）、垃圾识别。
- **行为侧**：刷屏频率、群发相似内容、定向骚扰模式。
- **关系侧**：**持续举报他人**（举报密度/举报准确率）、被多人拉黑、被举报集中度。

### 5.2 举报治理（防"举报武器化"）
- 举报本身是**双刃剑**：既要鼓励举报，又要防"用举报打击正常用户"。
- 设计：
  1. **举报计入信誉**：举报准确 → 信誉加成；诬告/滥举报 → 信誉扣分（见 §6）。
  2. **举证门槛**：重大举报需附证据（上下文截图/引用）。
  3. **冷启动保护**：低信誉新用户的举报权重低，需长期正确举报才提高权重。

### 5.3 分级处置（不搞一刀切）
| 级别 | 触发 | 处置 | 可申诉 |
|------|------|------|-------|
| 提示 | 首次轻微违规 | 私信提醒，记 1 次 | ✅ |
| 限流 | 频发 | 限发言频率 N 天 | ✅ |
| 禁言 | 恶意/反复 | 禁言 7~30 天 | ✅ |
| 封禁 | 严重（诈骗/刷分/持续侵害） | 全网封禁 + 信誉清零 | 人工复核 |

### 5.4 正常用户筛选（核心价值）
- 以**综合信誉分 + 行为画像**筛出"正常用户池"，正常用户获得：
  - 更高消息/带宽配额、优先进入游戏大厅、中继加速资格。
- 恶性个体（刷分、恶意举报、诈骗）被降权/隔离，避免污染社区。

## 6. 补强设计 ⑤：信誉分 + 防刷分（E5/E6）—— 本文重点

**核心思想：信誉分必须"难刷、易损、可追溯、只认长期"才有价值。单向棘轮：正常行为缓慢加分，破坏行为即刻扣分并留痕。**

新增模块：`reputation/engine`（计分）+ `reputation/audit`（审计）

### 6.1 信誉分的构成（多维，不单一）
```
信誉分 = 权重(贡献量) × 行为分 × 时间衰减 × 共识锚定
```
| 维度 | 说明 | 影响方向 |
|------|------|---------|
| 行为分 | 正常发言/内容质量/完成任务质量 | 加分 |
| 贡献量 | 提供算力/带宽/中继/存储 | 加分 |
| 破坏记录 | 恶意评论、刷分、诬告、诈骗、异常行为 | **即刻扣分** |
| 时间衰减 | 越久越稳的分权重越高 | 长期才有效 |
| 共识锚定 | 多节点对"扣分/加分事件"交叉验证后才入账 | 防单一节点操控 |

### 6.2 防刷分机制（对应 E6 生死线）
1. **不对称更新（棘轮）**：
   - 加分：**缓慢、封顶、需长期**（如每周最多 +X，且须累计在线/活跃时长达标）。
   - 扣分：**即刻、可叠加、可连续**（一次重大违规直接扣到红线）。
   - → "刷分刷不动，作恶立刻掉"。
2. **新增账号识别（防开小号刷）**：
   - 设备指纹 + 行为聚类：同一设备/同 IP 段/同行为模式 → 判定为小号关联。
   - 小号共享信用额度，且新号信誉从低位起步，**无法通过开小号绕过惩罚**。
3. **证明"真身份"**：信誉分绑定**长期身份密钥**，非一次性匿名号（见 §7）。
4. **时间权重**：**信誉分与账号年龄/在线时长强相关**——新号权重低，只有**长期维持正常**才逐渐累积到高信用，杜绝"一天刷满"。
5. **扣分留痕可审计**：所有加减分写入**签名账本**（append-only），任何人可查不可篡改。

### 6.3 防"贡献量刷量"（针对算力/带宽/中继激励）
- 双向校验：任务结果要**交叉验证**（多副本一致才算贡献有效）。
- 中继流量要**收端确认**（接收方回报"确实收到 N 字节"才计贡献），防止自刷流量。
- 恶意节点（返回错结果/假流量）除扣分外，信用**冻结期**内不得承接高价值任务。

### 6.4 信誉分生命周期
```
新用户(基础分) → 长期正常 → 稳步升分 → 高信用(优先资源)
                    ↘ 任一破坏 → 即刻扣分 + 留痕 → 降权/限流/封禁
```

## 7. 补强设计 ⑥：安全性强化（贯穿全篇）

### 7.1 数据加密
- **身份**：Ed25519 密钥，私钥本地 Keystore。
- **传输**：WebRTC DTLS/加密信道。
- **存储**：本地 + 云端 + 115 冷存**一律加密**（用户公钥加密），云端/115 只存密文。

### 7.2 抗作恶
- 计算结果多副本交叉校验（F5）。
- 信誉事件多节点共识后才入账（防单一节点操控）。
- 中继只转发不落盘（防中继窃取内容）。

### 7.3 抗刷/抗滥用
- 防刷分见 §6.2。
- 防垃圾/恶意内容见 §5。

## 10. 新增/更新风险清单

| 等级 | 风险 | 规避 |
|------|------|------|
| HIGH | 中继节点作恶/偷流量 | 只转发不落盘 + 收端确认 + 双向校验 |

| MEDIUM | 冷启动（新用户无信誉） | 分级处置 + 举报权重分级，保护正常新用户 |

## 11. 关键设计取舍说明（对张浩东关切点的直接回应）

1. **"个体不稳，谁来补"** → 冗余副本 + 健康检测 + 自动 failover，服务不因单点掉线而中断。
2. **"普通电脑能否当中转加速"** → 能，志愿者中继网格 + 多路径，复用空闲带宽做社区加速，等价于"去中心化 P2P 加速/CDN"。
3. **"本地存了，云端/115 要不要"** → 要，三层存储（本地热存 + 云端 + 115 冷备），加密归档、防丢失、可恢复。
4. **"信誉分怎么防刷"** → 单向棘轮（加分慢封顶、扣分即刻）+ 长期时间权重 + 小号关联 + 贡献双向校验 + 全量留痕审计。
5. **"识别恶意评论/持续举报者"** → 多维信号聚合 + 举报本身也记信誉（防诬告）+ 分级处置 + 筛出正常用户池。

# 13 · 专门解决 bug 的角色 · 能力评测方案

> 状态：v0.1 草案
> 目的：验证「专门解决 bug 的角色」（带增强壳）的修复能力，是否优于
>       直接调用外部 CodeBuddy 或 DeepSeek v4 flash，从而判定「壳」是否生效。
> 依赖：M1 最小可测代码基（`packages/core`）已跑通（11 项测试全通过）

---

## 1. 评测目标

回答三个问题：

| 问题 | 判定方式 |
|------|----------|
| Q1 带壳 bug 角色**能否修对**？ | 同一批 bug 任务，修复后测试是否全绿 |
| Q2 带壳 bug 角色**是否优于基线**？ | 与 DeepSeek v4 flash / 外部 CodeBuddy 同批任务对比修复通过率 |
| Q3 壳的机制**是否真正生效**？ | 逐项核对「评审-修复闭环护栏」在真实修复中被遵守 |

---

## 2. 评测集设计（bug-bench）

在 `bug-bench/cases/` 下每份用例 = 一个**含真实 bug 的代码 + 对应测试断言**。

| 用例 | 模块 | bug 类型 | 对应测试断言 |
|------|------|---------|-------------|
| case-01 | session | CRDT 收敛顺序错乱 | 两节点合并后序列必须一致 |
| case-02 | identity | 验签被绕过/防篡改失效 | 篡改后必须验签失败 |
| case-03 | policy | 联网策略判断反了 | offline 必须禁止广播 |
| case-04 | transport | 消息丢失/漏投递 | 对端必须收到消息 |
| case-05 | session | 消息类型校验缺失 | 非法类型必须被拒绝 |

> 每个用例可通过 `bug-bench/run.js --case case-01` 独立复现：加载含 bug 实现 → 跑对应测试 → 输出 ✅/❌。

---

## 3. 评测指标

| 指标 | 定义 | 目标 |
|------|------|------|
| 修复通过率 | 修复后通过测试的用例数 / 总用例数 | 带壳角色应显著高于基线 |
| 平均修复轮次 | 平均多少次「评审→修复」闭环才通过 | 带壳角色应更少（默认直接改） |
| 回归率 | 修复 A 用例时是否破坏其他用例 | 越低越好（壳要求每修固化断言） |
| 壳机制遵守度 | 默认直接改 / 10 轮护栏 / 钩子没 bug 就停 是否被遵守 | 逐项 ✅/❌ |

## 4. 对比基线

| 角色 | 说明 | 来源 |
|------|------|------|
| **被测：专门解决 bug 的角色** | 带「评审-修复闭环护栏」壳的 CodeBuddy | `dongdongxiaozu/youxikaifaxilieagent` |
| 基线 A：DeepSeek v4 flash | 无壳、直接问答式修复 | `cnpc/deepseek-harness` |
| 基线 B：外部 CodeBuddy | 无项目护栏、通用代码助手 | 外部/通用 NPC |

**控制变量**：同一批用例、同一测试信号灯、同一复现入口，仅切换修复执行者。

---

## 5. 执行流程（走正常管线）

```
① 经理划分工作包（issue.open → 游戏向经理 拆解）
   └─ 产出 M1 代码基（已跑通，见 packages/core）
② 埋入评测 bug（bug-bench/cases/*）
   └─ 测试信号灯由绿转红（CI 红灯阻塞）
③ 召唤「专门解决 bug 的角色」（带壳）修复
   └─ 遵循「评审-修复闭环护栏」：默认直接改 → 重推 → 测试回绿 → 钩子没 bug 就停
④ 同批任务跑基线（DeepSeek v4 flash / 外部 CodeBuddy）
   └─ 同一测试信号灯判分
⑤ 汇总对比 → 输出「壳是否生效」结论
```

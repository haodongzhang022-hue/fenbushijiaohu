## 1. 身份/密钥/抗作恶审计（identity/verify）

### 🔴 1.1 校验无节点身份绑定 → Sybil 攻击可伪造多数一致

- **文件**：`packages/compute/src/verify.js` L23-45
- **风险描述**：`verify()` 仅对 `results` 数组做「多数一致」统计，结果**未与提交副本的节点身份绑定**，也未校验副本是否来自互不相同的独立节点。`compute.collect()` 不校验调用者身份、不限制每节点可注入副本数，任何单一攻击者可用多个假身份批量提交同一错误结果，使 `agreement >= minReplicas(默认 2)`，伪造出「可信」结果。
- **攻击场景**：攻击者注册 N 个假节点，对某计算任务批量提交 `{ result: 恶意值 }`，使 majority 达到阈值，`trusted=true`，下游据此采信被篡改的计算结果。
- **OWASP**：A01 失效的访问控制 / A04 不安全设计（信任边界缺失）。
- **修复建议**：
  ```js
  // verify 应接收 { nodeId, result } 对，先做身份去重与签名校验
  verify(collected /* [{nodeId, sig, result}] */) {
    const byNode = new Map();       // 每个身份只计一次
    for (const { nodeId, result } of collected) {
      if (!verifySignature(nodeId, result)) continue; // 先验签
      if (!byNode.has(nodeId)) byNode.set(nodeId, result);
    }
    // 仅当 distinctNodes >= minReplicas 才计算多数
  }
  ```
  - `collect()` 需带上 `nodeId` + 结果签名，去重同一节点重复提交。
  - `minReplicas` 应 `> 1` 且要求「独立节点数」而非「结果条数」。

### 🔴 1.2 结果键仅用 `JSON.stringify(r)`，无规范化 → 等价结果被判为不一致

- **文件**：`packages/compute/src/verify.js` L29-38
- **风险描述**：对象结果的键顺序不同（`{a:1,b:2}` vs `{b:2,a:1}`）会被判为不同 `key`，同一语义结果的副本因序列化差异无法达成多数 → 误判 `trusted=false`（可用性风险），或反之被构造出「恰好一致」的恶意值（一致性风险）。
- **攻击场景**：攻击者构造键序特殊的结果使字符串碰撞多数；或正常节点因对象键序差异无法通过校验，任务持续失败。
- **OWASP**：A04 不安全设计 / CWE-697 不正确的比较。
- **修复建议**：对结果做**规范化排序后序列化**（`JSON.stringify` 前对键排序），并限制结果类型为可比较的标量或规范化对象。

### 🟠 1.3 任务 id 为 64-bit 哈希截断 + 无提交者绑定

- **文件**：`packages/compute/src/compute.js` L31、L38-40
- **风险描述**：任务 `id = sha256(input).slice(0,16)`（16 个 hex 字符 = **64 bit**，熵仅 64 bit），碰撞/预计算风险偏高；且 id 由 input 直接推导，攻击者可对已知 input 预测 id，进而污染/覆盖他人已登记任务（`submit` 直接 `set`，同 id 会覆盖 `_tasks` 与 `_results`）。任务未绑定提交者身份。
- **攻击场景**：攻击者用相同 input 再次 `submit`，覆盖原任务及其已收集结果（`_results.set(id, [])` 清空），或猜测 id 在 `collect` 注入脏结果。
- **OWASP**：A04 不安全设计 / CWE-330 不充分随机性。
- **修复建议**：
  - id 改用完整随机熵（`crypto.randomBytes(16).toString('hex')`），或 `full sha256`（保留 256-bit）。
  - `submit` 检测 id 冲突：已存在则拒绝或返回现有任务，不静默覆盖。
  - 任务结构加入 `submitter`/`owner`，后续 `collect`/`split` 校验操作者身份。

### 🟡 1.4 `JSON.parse(bestKey)` 反序列化结果未做净化（存疑）

- **文件**：`packages/compute/src/verify.js` L42
- **风险描述**：对多数一致结果执行 `JSON.parse`。`JSON.parse` 本身不执行代码，但若副本结果含 `__proto__`/`constructor.prototype` 等键，且下游以 `{...result}` / `Object.assign` 等方式合并，存在**原型污染**风险。是否真实危害取决于下游消费方式。
- **OWASP**：A08 软件与数据完整性故障 / CWE-1321。
- **修复建议**：解析后递归移除危险键，或用 `Object.create(null)` 承载解析结果，并在消费端禁止对不可信对象做 `__proto__` 合并。

## 2. 信誉分防刷审计（reputation）

### 🔴 2.1 `penalize` 未校验 points 符号 → 传负值即「扣分变加分」，可无上限刷分

- **文件**：`packages/compute/src/reputation.js` L35-38
- **风险描述**：`penalize(points)` 直接 `this.score -= points`，**未校验 `points >= 0`**。调用方（或恶意节点路径）传入 `penalize(-1)` 会执行 `score -= (-1)` 即 **`score += 1`**，绕过 `reward` 的单次上限 `Math.min(points, 5)`，实现**无限刷分**。且 `reward` 的单次上限仅限 reward 路径，penalize 路径完全无节流。
- **攻击场景**：攻击者控制某节点计算路径，对目标节点调用 `penalize(-100)` 直接加分，或反复 `penalize(-1)`，将任意节点刷到 `trusted`（cap=100），从而绕过信誉分治理、获得高信誉准入资格。
- **OWASP**：A04 不安全设计 / CWE-697 不正确的比较。
- **修复建议**：
  ```js
  penalize(points) {
    if (typeof points !== 'number' || !Number.isFinite(points) || points <= 0) {
      throw new TypeError('penalize 仅接受正数');
    }
    this.score = this.score - points;
    return this.score;
  }
  // reward 同理校验 points >= 0 且有限
  reward(points) {
    if (typeof points !== 'number' || !Number.isFinite(points) || points <= 0) {
      throw new TypeError('reward 仅接受正数');
    }
    this.score = Math.min(100, this.score + Math.min(points, 5));
  }
  ```

### 🟠 2.2 信誉分为纯内存单机模型，无持久化/签名/审计溯源 → 可被篡改与高频刷

- **文件**：`packages/compute/src/reputation.js` 全文件
- **风险描述**：`this.score` 是公开可写字段，任何持有实例的代码可直接 `r.score = 100` 篡改；且无持久化、无事件溯源，无法审计扣分/加分的因果链条。防刷核心依赖「可信调用方」这一未实现前提。评分**无时间维度/无频率节流**，即使校验符号，也无法防高频小步刷分。
- **攻击场景**：恶意节点组件直接改写 `score` 字段；或高频调用 `reward(1)` 反复刷分（若 `reward` 受单次上限，但无时间窗口）。
- **OWASP**：A04 不安全设计 / CWE-353 认证缺失。
- **修复建议**：
  - 评分对调用方隔离：只暴露 `reward/penalize` 接口，字段设为私有（`#score`），禁止外部直接写。
  - 引入**评分事件日志**（append-only，含时间戳与触发原因），供审计与回滚。
  - 引入**时间窗口节流**：如「每自然日 reward 累计上限」，超出拒绝；结合档位 cap（`limited=5 / regular=20 / trusted=100`）在接入任务时按 `tier().cap` 限制并发任务数（防刷的硬约束）。
  - 后续阶段将评分持久化并绑定节点身份签名（防篡改与抵赖）。

## 3. 内容去重/存储一致性安全审计（content/storage）

### 🔴 3.1 去重指纹截断到 64-bit → 碰撞可致内容错误去重/替换（完整性破坏）

- **文件**：`packages/content/src/content.js` L59-61、L42-46
- **风险描述**：`_hash` 用 `sha256(piece).slice(0,16)`（16 hex = **64 bit**），作为去重唯一寻址键。64-bit 指纹在规模化内容池下**碰撞概率不可忽略**（生日攻击，约 2^32 量级条目即达 50% 碰撞）。`register()` 以 `hash` 判定去重，碰撞即把不同内容误判为「重复」而**丢弃/不登记**新内容，或 `lookup()` 取回被碰撞覆盖的旧/错误分片，破坏内容完整性。分片大小默认仅 4 字符，指纹空间远大于内容空间，碰撞概率被进一步放大。
- **攻击场景**：攻击者构造与已登记分片同 hash 但不同内容的恶意分片，触发去重命中后 `lookup` 返回被替换内容；或利用碰撞拒绝合法内容登记（内容投毒）。
- **OWASP**：A08 软件与数据完整性故障 / CWE-328（使用可逆哈希）或 CWE-326（不充分熵）。
- **修复建议**：
  - 指纹用完整 `sha256`（64 hex / 256-bit），勿截断；如必须截断，保留 ≥ 128 bit（32 hex）。
  - `register` 命中碰撞时**校验原存储内容与新增内容是否一致**：一致才去重，不一致则抛冲突错误，而非静默跳过。
  ```js
  register(chunk) {
    const prev = this._store.get(chunk.hash);
    if (prev) return prev.data === chunk.data;  // 碰撞且不同 → 拒绝
    this._store.set(chunk.hash, chunk);
    return true;
  }
  ```

### 🟠 3.2 去重存储无 hash 与 data 一致性复核 → 缓存投毒/内容污染

- **文件**：`packages/content/src/content.js` L42-51、`packages/content/src/storage.js` L26-37
- **风险描述**：`register`/`put` 信任调用方传入的 `chunk.hash` 与 `data` 的对应关系，**不在写入/读取时重算 hash 校验**。恶意调用方可用任意 `data` 配一个「看似合法」的 `hash` 键，`lookup` 返回后下游按 hash 信任内容，造成内容完整性破坏。`storage.js` 缓存同样无完整性/来源校验，可被任意 `put` 投毒。
- **攻击场景**：攻击者向缓存 `put('著名分片hash', 恶意内容)`，合法消费者 `lookup/get` 取到被投毒内容，用于视频/内容分发造成污染传播。
- **OWASP**：A08 软件与数据完整性故障。
- **修复建议**：
  - `register` 内部对 `data` 重算 `hash(data)`，与 `chunk.hash` 比对，不一致则拒绝。
  - 内容分发链路对取回内容做**完整性校验**（比对内容 hash）后再使用。
  - `storage.put` 由受信内部逻辑调用，不接受外部任意 key-value 直写，或对 key 增加前缀/命名空间隔离。

### 🟡 3.3 LRU 命中率统计语义偏差（仅统计 get，不含 put 命中）

- **文件**：`packages/content/src/storage.js` L26-37、L39-49、L56-59
- **风险描述**：`hitRate()` 只统计 `get` 的命中/未命中，`put` 已存在 key（覆盖）时不更新 `_hits`。这在语义上使「重复 put 同一 key」不被计为命中，命中率失真，可能误导缓存治理决策。属低危可用性/一致性偏差，非直接安全漏洞，但影响后续容量与去重调优的依据可靠性。
- **OWASP**：不适用（可用性观测缺陷）。
- **修复建议**：明确命中率口径（仅读命中 或 读+写命中），并在文档注释中说明；若按「访问命中」则 `put` 覆盖已存在 key 时应计 `_hits`。

## 4. 关联风险（M2/M2a 中继链路，顺带审计）

### 🟠 4.1 中继节点容量永占不释放 → DoS（中继耗尽）

- **文件**：`packages/relay-mesh/src/mesh.js` L34-44
- **风险描述**：`findRelay()` 选中中继后 `chosen.capacity -= 1`，但**没有任何释放/归还机制**（无 `release`、无定时过期）。节点容量会单调递减直至耗尽，所有中继 `capacity<=0` 后 `findRelay` 恒返回 `null`，全网中继能力被耗尽。
- **攻击场景**：攻击者反复调用 `requestRelay`/`findRelay` 占用中继容量，直至耗尽，使其他合法节点无法获得中继链路。
- **OWASP**：A04 不安全设计 / CWE-400 未受控资源消耗。
- **修复建议**：为容量占用增加**租约/超时释放**（`TTL` 或 `release(relayId)` 归还），`findRelay` 返回的 `desc` 绑定有效时长，过期自动归还容量。

### 🟡 4.2 志愿者自宣称健康 + 无身份信誉校验 → 中继 Sybil / 恶意中继

- **文件**：`packages/relay-mesh/src/mesh.js` L14-17、`packages/net-policy/src/relay.js` L45-49
- **风险描述**：`offer()` 直接 `healthy: true` 登记任意 `relayId`，无身份证明/无信誉门槛。恶意节点可批量声明「健康高容量」中继，劫持流量。`forwardVia` 中继「只转发不落盘」承诺为代码注释，实际返回 `bytes: JSON.stringify(msg).length`——中继可见**明文消息长度**，且若无端到端加密（E2EE），中继志愿者可窥见**明文内容**，存在隐私泄露。
- **攻击场景**：恶意节点自荐为中继，截获/分析经其转发的明文消息（流量分析 + 内容窥探）；或批量注册假中继抢占 `findRelay` 选路。
- **OWASP**：A02 加密失败（敏感数据明文传输）/ A01 失效的访问控制。
- **修复建议**：
  - 中继登记绑定节点信誉分与身份签名，`offer` 前校验信誉门槛与健康证明。
  - 引入端到端加密（E2EE），中继仅见密文与元数据，`forwardVia` 不返回明文 `bytes` 明细或对长度做掩码/加噪声。
  - `forwardVia` 校验调用方是否有权使用该 `targetId` 链路（防任意目标放大转发）。

## 6. 审计结论与放行建议

### 结论：**需修改后通过（needs_modification）**

本代码基为「最小可测纯逻辑包」，未引入网络 I/O 与外部输入边界，当前未发现**可直接触发的严重漏洞**，测试信号灯可继续用于门禁。但存在多处**高危设计缺陷**，若在 M2/M3/M4 投产或接入真实网络层前不修复，将直接构成安全风险：

- **必须修复（高危，建议纳入本 PR 或立即跟进 PR）**：
  1. `verify.js` 引入节点身份绑定 + 签名校验（1.1）；
  2. `reputation.js` 的 `penalize/reward` 校验输入符号与有限性（2.1）；
  3. `content.js` 指纹去重改用完整 sha256 或 ≥128bit，并做碰撞内容一致性复核（3.1）。

- **强烈建议修复（中危）**：1.3 任务 id 熵与冲突；2.2 信誉分节流/溯源；3.2 hash-data 复核；4.1 中继容量释放。

- **放行门槛建议**：CP3 放行前，高危项 1.1/2.1/3.1 应已修复并通过对应测试；中危项给出修复排期。
